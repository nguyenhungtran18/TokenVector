## Body

TokenVector is a Python-syntax language that compiles ahead-of-time to
.NET CIL — no interpreter, no GIL, standalone `.exe` output. Its compiler
is self-hosted (written in TokenVector itself).

Calling .NET libraries from a new language usually means hand-writing
interop bindings — the standard cost every new language on a runtime
pays before it's actually useful. TokenVector has a tool for this,
`tkv-bind`: point it at any `.dll`, it reflects the public surface and
emits ready-to-use binding declarations. Until this week it had only
been run against the .NET Framework BCL (`System.dll`). I ran it against
a real, published NuGet package for the first time to see what breaks.

**Target: Newtonsoft.Json 13.0.3**, downloaded straight from nuget.org
(not vendored, not simplified).

```bash
python tools/tkv_bind/main.py --dll Newtonsoft.Json.dll --out bindings.tkv
```

First run: it worked with zero code changes — `Assembly.LoadFrom` inside
the reflector doesn't care what assembly you hand it. It bound ~40
classes (exceptions, attributes, converters) and skipped 253 members it
couldn't map (mostly generic methods and LINQ-to-XML types — expected).

The two most important methods in the entire library, though — the ones
almost every real use of Newtonsoft.Json goes through —
`JsonConvert.SerializeObject(object)` and
`JsonConvert.DeserializeObject(string)`, were both in the skip list.

## What was actually broken

Digging into why (not guessing — verified against real compile+run
output each time):

**1. `object`/`type` parameters were rejected on module-level extern
methods**, even though the compile-time machinery to handle them
(boxing value types before passing them as `object`, emitting the right
CIL type text for `System.Type`) had already been built and tested for
a different call path (methods on already-bound handle types). It was
a stale validation check, not a missing feature — removing it was safe
because the codegen underneath was already exercised.

**2. Assembly version references silently dropped the version number**
when the assembly wasn't signed with a known public key token — which
is the normal case for third-party NuGet packages. The generated IL
asked the CLR to load "any version" but the loader actually resolved
that as version `0.0.0.0`, and rejected the real `13.0.0.0` DLL with a
`FileLoadException`. Fix: always emit the real version when the caller
provides one, signed or not.

**3. Flipping on the object/type support surfaced a second, unrelated
bug**: passing one bound type as a parameter to a method on *another*
bound type dropped the binding entirely in one specific code path. Found
only because a regression test written for a completely different
purpose (Phase 9e, months earlier) started failing.

## Result

After the fix, running `tkv-bind` again on the same DLL:

```
before: 253 skipped (incl. SerializeObject / DeserializeObject)
after:  248 skipped (SerializeObject / DeserializeObject now bind)
```

And a real round-trip, compiled and run as a standalone `.exe`, calling
the real Newtonsoft.Json DLL:

```
$ ./program.exe '{"a":1,"b":"x"}'
{"a":1,"b":"x"}
```

No mocks, no simplified reimplementation — that's the actual JSON.NET
library, called from a `.tkv` source file, through bindings the tool
generated by reading the DLL, not by anyone reading the docs and typing
out signatures by hand.

## What's still rough

- Passing a numeric literal directly into an `object`-typed parameter
  (`describe(1)`) currently fails with an unhelpful `KeyError` instead
  of a clean error — assigning it to a variable first works
  (`x = 1; describe(x)`). Known, not yet fixed.
- Generic methods (`DeserializeObject<T>`) aren't supported — you get the
  non-generic, `object`-returning overload instead.
- LINQ-to-XML-adjacent types (`JToken`, `XNode` interop) don't map yet.

## Why this matters more than the specific fix

The interesting part isn't Newtonsoft.Json specifically — it's that
`tkv-bind` turned a "point it at a DLL and see what happens" exercise
into 3 concrete, fixable bugs inside a couple of hours, on a library
nobody on the project had touched before. That's the actual test for
whether an auto-binder generalizes past the one assembly it was built
against.
